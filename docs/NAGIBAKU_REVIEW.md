# ナギバク：企画審査・台本監修・違和感監査（毎回の手順）

> 目的：AIが作った企画やセリフの不自然さを、ユーザーが毎回見つけて直している状態を減らす。面白さをAIだけで保証する仕組みではない。最終判断はユーザー。
> セリフの書き方そのものは `docs/NAGIBAKU_DIALOGUE_VOICE_RULES.md`、過去の指摘は `docs/NAGIBAKU_LESSONS.md`。**作業の前に必ず LESSONS を読む。**

## 制作フローの中での位置
| いつ | やること | 結果を置く場所 |
| --- | --- | --- |
| ネタを集めたあと・台本の前 | **1. 企画審査** | `docs/proposals/<回>_kikaku.md`（候補ごとに数行）→ ユーザーが採用を決める |
| 台本を書く前 | **2. 立場を決める**（章ごとのメモ） | 台本ファイルの頭の `#` コメント |
| 台本を書き終えたら・声を作る前 | **3. 違和感監査** → 直せるものを直す | `docs/proposals/<回>_audit.md` |
| ユーザーから修正が入ったら | **4. 履歴に足す** | `docs/NAGIBAKU_LESSONS.md` |

声を作ったあとに台本を直すと作り直しが増えるので、監査は必ず声の前にやる。

---

## 1. 企画審査（台本を書く前）
候補ごとに5つを ◯／△／✕ で判定する。✕ が1つでもある候補は、そのまま出さず代案を付ける。

| # | 問い | ✕ の例 |
| --- | --- | --- |
| 1 | 実際に打っている人が気になる話か | 業界団体の組織図、資料の数字の推移だけ |
| 2 | テーマを一言で言えるか | 「〜と〜の関係と、その背景」 |
| 3 | タイトルが口に出して気持ちよく、見ただけで意味が分かるか | 「エヴァの継続率はなぜ上がって下がってまた上がったのか」 |
| 4 | 懐かしさ・意外性・共感・笑い・怒りのどれかが動くか | 「整理するとこうなる」だけ |
| 5 | 情報を並べるために作った疑問になっていないか | 答えは出せるが、誰も聞いていない問い |

候補ごとに書くのはこの3行だけ（長くしない）：
- **狙う視聴者**：例「5年以上エヴァを打ってきた人」
- **見たくなる理由**：例「あの台がなぜ消えたのかを知りたい」
- **懸念**：例「史実が薄い」「同じ題材の動画が多い」

代案も同じ5つで判定し、史実（出典）と視聴者の関心を確かめてから出す。採用はユーザーが決める。

## 2. 台本を書く前に、2人の立場を決める
章ごとに台本の頭へ `#` で1〜2行メモする（台本には書き込まない＝セリフで説明しない）。
- **ナギ**（白うさぎ・標準語）：この話のどこに引っかかるか。データ派の打ち手として何を計算・比較したくなるか。中立の説明係にしない。
- **バク**（橙猫・関西弁）：打ち手としての実感。ホールで実際に何をしていて、何に困って／喜んでいるか。無理な逆張りはさせない。
- **知らないことは知らないと言わせる。** 分かったふりの相づち、説明のための質問、毎回の賛否両論は入れない。
- 各セリフに「なぜこのキャラがここでこれを言うか」が説明できること。できない行は削るか、言う人を替える。

## 3. 違和感監査（台本を書き終えたら）
**書いた流れから切り離して行う。** 台本ファイルと `docs/NAGIBAKU_LESSONS.md` だけを読み直し、「この台本の粗を探す係」として全セリフを見る（書いたときの意図の説明は参考にしない）。

| 観点 | 見ること |
| --- | --- |
| A 業界知識 | ホールの設備（台間サンド・各台計数・会員カード・貯玉など）、実際の遊技の動き、業界用語、機種スペック、交換率・三店方式、決済の仕組み |
| B 打ち手心理 | その場面で打ち手が本当に言うか。お金の感覚（負けた日・給料日・追加投資）、ホールでの行動、期待と不満 |
| C キャラの自然さ | 優等生発言、意味のない相づち、解説のためだけの質問、機械的な賛否両論、教訓でまとめる締め |
| D 言葉のセンス | 語感、冗長、説明くささ、ツッコミの弱さ、要らない専門用語、書き言葉 |
| E エンタメ性 | 平坦な所、新しい発見・笑いがない章、同じ型の繰り返し |

報告の形（`docs/proposals/<回>_audit.md`）：
- 深刻な順に **最大10件**。1件ずつ **問題セリフ（行ID）→ 理由（観点A〜E）→ 修正案**。
- 事実が確かめられないものは推測で直さず **「要確認」** と書いて残す（出典 `SOURCES.md` で確認できたものだけ直す）。
- 直すのは重要度の高いものから。元の笑い・オチ・ユーザーが気に入っている箇所は残す。
- **監査は1回で終える。** 直した台本をもう一度まるごと監査し直すループにはしない（直した行だけ読み直して、新しい不自然さが入っていないか確かめる）。
- 最後に「変更前→変更後」の対照表と、今回新しく見つかった問題の種類を書く。

## 4. 修正履歴に足す（ユーザーから指摘が入ったら）
- `docs/NAGIBAKU_LESSONS.md` の「ユーザーの指摘」に、**何が起きたか／なぜダメか／再発を防ぐ原則** を書く。個別の言い換えだけで終わらせない。
- AIの監査で見つけたもの・AIの推測は「監査で見つけた候補」に分けて書く。ユーザーが同意したら「ユーザーの指摘」側へ移す。
- 原則が増えて重なったら、まとめて短くする（ファイルを長くし続けない）。
